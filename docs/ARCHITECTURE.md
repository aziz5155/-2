# المعمارية (Architecture)

## الفصل بين الطبقات

```
app/          → UI فقط (شاشات Expo Router). لا تكتب فيها منطق أعمال مباشرة.
src/services/ → طبقة الخدمة: كل استدعاء Supabase (قراءة/كتابة/RPC) يمر من هنا.
src/stores/   → حالة محلية بحتة (الثيم، اللغة، الجلسة) — zustand.
react-query   → طبقة التخزين المؤقت وحالات التحميل/الخطأ لبيانات الخادم.
Supabase      → المصدر الوحيد للحقيقة: القاعدة + RLS + دوال RPC + Edge Functions.
```

القاعدة العملية: أي شاشة تحتاج بيانات تستدعي دالة من `src/services/*` عبر
`useQuery`/`useMutation`، ولا تكتب استعلام Supabase مباشرة داخل مكوّن JSX.

## لماذا منطق النقاط في قاعدة البيانات لا في التطبيق؟

لو كان "خصم النقاط عند الاستبدال" مكتوبًا في كود التطبيق (اقرأ الرصيد → تحقق
أنه كافٍ → اطرح → احفظ)، فإن ضغط الطفل على "استبدال" مرتين بسرعة (أو انقطاع
الشبكة أثناء الحفظ) قد يؤدي لخصم مضاعف أو رصيد سالب خاطئ. لذلك:

- كل عملية تمس النقاط (منح، خصم، اعتماد مهمة، استبدال مكافأة) هي **دالة واحدة
  ذرية** في Postgres (`SECURITY DEFINER`) تُنفَّذ بالكامل داخل معاملة واحدة
  (transaction)، مع قفل صف (`FOR UPDATE`) عند القراءة قبل الكتابة — فلا يمكن
  لطلبين متزامنين أن يخصما نفس الرصيد مرتين.
- الجدول `point_transactions` هو سجل **append-only فقط**: لا `UPDATE` ولا
  `DELETE` مسموحين لأي طرف، حتى ولي الأمر. الرصيد المعروض (`points_balance`)
  هو مجرد ذاكرة تخزين مؤقت (cache) يُحدَّثها Trigger تلقائي بعد كل قيد جديد.

## لماذا Row Level Security وليس فحص الصلاحيات في التطبيق فقط؟

طلب المشروع صراحة: "لا تعتمد على إخفاء الأزرار فقط". حتى لو أُزيلت الشروط من
واجهة التطبيق (أو استُدعي الـ API مباشرة بأداة خارجية)، فإن قاعدة البيانات
نفسها ترفض أي قراءة أو كتابة لا تخص عائلة المستخدم الحالي. هذا مطبَّق عبر:

1. **RLS مفعّل على كل جدول** بدون استثناء.
2. **دوال مساعدة** (`is_family_parent`, `is_family_child`, `current_child_id`)
   تُستخدم داخل كل سياسة (Policy) بدل تكرار المنطق.
3. **الجداول الحساسة** (`point_transactions`, `task_completions`,
   `reward_redemptions`, `child_achievements`, `activity_events`,
   `notifications`, `subscriptions`) لا تملك أي صلاحية `INSERT/UPDATE/DELETE`
   مباشرة من التطبيق إطلاقًا — الكتابة الوحيدة الممكنة هي عبر دوال RPC.

## حساب الطفل بدون بريد إلكتروني

الطفل يحتاج جلسة مصادقة حقيقية (لتعمل RLS بشكل صحيح ولتُنسب الأفعال إليه)،
لكن المشروع يطلب صراحة عدم إجبار الطفل على امتلاك بريد إلكتروني. الحل:

1. عند إضافة طفل، تُنشئ **Edge Function** (`create-child`, تعمل بصلاحية
   Service Role) مستخدم Auth حقيقي ببريد داخلي غير معروض
   (`child.<uuid>@internal.familysuccess.app`) وكلمة مرور = الرمز السري
   (PIN) المكوّن من 4 أرقام الذي يختاره ولي الأمر.
2. دخول الطفل يتم بخطوتين عبر Edge Function باسم `child-login`:
   - `list`: يُدخل كود العائلة فقط، فيعرض له أسماء/صور الأبناء المسجَّلين
     (دون كشف البريد الداخلي لأي طرف).
   - `signin`: يختار اسمه ويدخل رمزه السري، فتتحقق الدالة من التطابق وتُصدر
     جلسة Supabase حقيقية.

بهذا الشكل، الطفل لا يعرف بريده الداخلي إطلاقًا، ولا يمكن لأي طرف إنشاء حساب
طفل من التطبيق مباشرة (لأن ذلك يتطلب Service Role الموجود فقط في السيرفر).

## القابلية للتوسع المستقبلي

البنية مصمَّمة لتستوعب لاحقًا بدون إعادة هيكلة:

- **أكثر من ولي أمر لنفس العائلة**: جدول `family_members` منفصل عن
  `families` من اليوم الأول تحديدًا لهذا السبب.
- **Apple Watch / Widgets / Siri Shortcuts**: طبقة `src/services` مستقلة عن
  الواجهة، فيمكن استدعاؤها من أهداف (targets) أخرى في نفس مشروع Xcode لاحقًا.
- **اشتراكات Premium حقيقية**: جدول `subscriptions` وواجهة `getSubscription`
  جاهزان؛ الخطوة المتبقية هي ربط Webhook من RevenueCat/App Store Server
  Notifications لتحديث الصف (سيرفريًا فقط — لا صلاحية تعديل من التطبيق).
- **إشعارات Push فعلية**: جدول `notifications` هو "صندوق بريد" داخلي جاهز؛
  إضافة الإرسال الفعلي تعني فقط ربط Expo Push Tokens وإرسالها من Edge
  Function عند إدراج صف إشعار جديد (Database Webhook).
